# CSM Notification Service

Go HTTP server (`net/http`, Go 1.26+), one role: an event-driven notification pipeline. `POST /events` publishes a domain event (case created, comment added, status changed, case assigned, incident created) to Azure Event Hub, and this same service's background consumer reads it back and sends the actual notification — email, a Google Chat alert, or a voice call. Extracted from `apps/csm-portal/backend/internal/notifications` — that backend no longer owns or calls any notification client. There used to also be a `POST /notifications` direct channel-command endpoint (a stub that only validated and never sent anything); it was removed once the event-driven path became the service's only real send mechanism — don't re-add a parallel direct-dispatch endpoint without confirming that's actually needed, since it would duplicate `dispatch.Dispatcher`'s send logic.

## Current scope — deliberately incomplete

The event-driven path (`POST /events` → event bus → `dispatch.Dispatcher`) **is real** — it sends actual emails, Google Chat alerts, and voice calls — but has two known, explicitly-flagged gaps:

- **No dead-letter topic.** `eventbus.Consumer` retries a failing record `handleAttempts` (3) times, then logs it at ERROR and commits its offset anyway — the record's content is only recoverable from Event Hub's own retention window after that. See the `TODO` in `eventbus.Consumer.handleAndCommit`.
- **SMS and direct call channels are unused.** `TwilioClient.SendSMS` has no caller anywhere in this service; `MakeCall` is only invoked by `handleIncidentCreated`. Both clients/methods exist and are tested (including live, via `cmd/twiliocheck`), just not wired to any event type yet.

Email recipient resolution is **not** a fixed env-configured list — every `case.*` payload carries its own `recipients` array, supplied by the caller (e.g. `csm-portal-backend`), since `dispatch.Dispatcher` has no `entity-service` client to resolve watchers/assignee/reporter itself. That's still short of "real" resolution (the caller has to already know the audience), but there's no `TEMP_*` env var or hardcoded test list to avoid pointing at real mailboxes anymore — `handler.validateEventPayload` rejects any `case.*` event published with an empty `recipients` list. This does **not** apply to `incident.created`'s Google Chat/call reactions — those already carry a real destination (a Chat space and a phone number) in the event payload itself, since there's no "recipient" concept to resolve for them the way there is for email.

## Why no `Auth` middleware

Like `integrations/csm-integration-service`, this service has no end-user identity to check — it's consumed by other backend services (and, later, a Kafka consumer) through Choreo's API Manager gateway, which owns the inbound trust boundary (subscription + client credentials) before a request ever reaches this app. Do not add inbound JWT/Bearer validation here without confirming that assumption no longer holds.

## Middleware chain

`SecurityHeaders → CorrelationID → Logger → Mux`

- `SecurityHeaders` (`internal/middleware/security_headers.go`): sets `X-Content-Type-Options: nosniff`, `Content-Security-Policy: upgrade-insecure-requests`, and `Strict-Transport-Security: max-age=31536000; includeSubDomains` on every response
- `CorrelationID` (`internal/middleware/correlation.go`): reads `X-CSM-Correlation-ID` from the incoming request or generates a UUID v4; ensures the ID carries a `cns-` prefix (CSM Notification Service) either way, without double-prefixing an ID that already has it; stores the ID in context for the slog handler; echoes the ID in the response header
- `Logger` (`internal/middleware/logger.go`): logs every completed request (method, path, status, elapsed) via slog

`middleware.ConfigureLogger()` must be called at startup — it wraps the default slog handler so every `slog.*Context(r.Context(), …)` call automatically includes `correlationID=<id>` when the context carries one.

## Notification channels

`internal/notifications` — one config/client pair per channel in its own file, since channels differ in upstream auth scheme:

- `EmailConfig`/`EmailClient`/`SendEmail` (`email.go`) — OAuth2 client-credentials auth against an external email notification service (`POST /send-email`)
- `GoogleChatConfig`/`GoogleChatClient`/`SendIncidentAlert` (`googlechat.go`) — a plain incoming-webhook URL per Google Chat space, no OAuth2 involved. `GoogleChatConfig.Spaces` is `[]GoogleChatSpace` (`{Product, WebhookURL}`), one space per product; `SendIncidentAlert` routes to the space matching `product` (case/whitespace-insensitive; unmatched returns an error, no fallback space)
- `TwilioConfig`/`TwilioClient`/`SendSMS`+`MakeCall` (`twilio.go`) — HTTP Basic Auth (Twilio Account SID/Auth Token; Twilio has no OAuth2 flow). One client, two methods, since sms and call are the same Twilio account/auth, just different REST resources (`Messages.json` vs `Calls.json`) via a shared private `do()`:
  - `SendSMS(ctx, to, body)` sends via the client's configured `MessagingServiceSid` if set (our account's real setup — a sender pool with opt-out/compliance handling), else its fixed `FromNumber`. If both are set, `MessagingServiceSid` wins
  - `MakeCall(ctx, to, message)` places a voice call that reads `message` aloud via a `<Say>` TwiML document built locally (`sayTwiML`, no external TwiML hosting needed) — always requires `FromNumber` as caller ID, since Voice has no `MessagingServiceSid` equivalent, regardless of whether `MessagingServiceSid` is set for sms. `<Say voice="..." language="...">` come from `TwilioConfig.Voice`/`Language` (`TWILIO_VOICE`/`TWILIO_LANGUAGE`, both optional — empty omits the attribute and uses Twilio's account default)
  - `TwilioConfig.APIBaseURL` overrides Twilio's REST API base (`TWILIO_API_BASE_URL`, defaults to `defaultTwilioAPIBaseURL` when empty — resolved once in `NewTwilioClient`, not read per-request). Not just a test seam: tests set it to an `httptest.Server` URL the same way a real deployment could point it at a regional Twilio edge endpoint

All three clients are constructed in `cmd/server/main.go` with `os.Getenv` (never `mustEnv`) for their config, since none is required for every deployment — a missing/invalid config only surfaces as an error the first time that channel is actually used. All three are handed to `dispatch.NewDispatcher`, which is the only thing that calls them (see "Current scope" above for `SendSMS`/`MakeCall`'s current usage gap).

A new channel gets its own `<Name>Config`/`<Name>Client` file in `internal/notifications` following the same pattern (or a new method on an existing client, if it shares that client's auth — as `MakeCall` does with `SendSMS`), then gets wired into `Dispatcher` for whichever event type(s) should trigger it — see "Adding a new event type" below.

## Event-driven notifications

Three packages implement the producer→bus→consumer pipeline; `internal/notifications` (templates + channel clients) is the last-mile sender this pipeline calls.

- **`internal/events`** (`events.go`) — the schema. `Type` is one of `case.created`/`case.comment_added`/`case.status_changed`/`case.assigned`/`incident.created` (`KnownTypes`). `Envelope{Type, EntityID, EventID, Payload}` is both the `POST /events` request body and the Kafka record value — `EntityID` is a case ID for the `case.*` types or an incident ID for `incident.created` (whatever the event is about, generically — it was named `CaseID` originally, renamed once `incident.created` made that name misleading). `EventID` is optional and currently unused (nothing validates or dedupes on it yet) — it exists purely so a caller can start generating one now, while nothing else consumes this schema yet; see its doc comment for the duplicate-publish scenario it's meant to eventually close. `Payload` is `json.RawMessage`, decoded into the `Type`-matching payload struct (`CaseCreatedPayload`, etc.) by whoever needs it (validation in the handler, rendering in the dispatcher). For the four `case.*` types, `validateEventPayload` also rejects a payload whose own `CaseID` disagrees with the envelope's `EntityID` — they must match, since `EntityID` is the partition key (see `internal/eventbus` below); a mismatch would key one case's data under another case's partition. Payloads are **denormalized on purpose** — every value a reaction needs is in the payload itself (names, titles, links, a phone number, and for the four `case.*` types, a `Recipients []string`), not just IDs, because there's no `entity-service` client to resolve anything from IDs yet. When that client exists, payloads should shrink to IDs and the dispatcher should resolve display data (and recipients) itself instead of requiring the caller to already know them — don't treat today's denormalized shape as permanent.
- **`internal/eventbus`** (`config.go`/`producer.go`/`consumer.go`/`logger.go`) — a thin wrapper around `github.com/segmentio/kafka-go` for Azure Event Hub's Kafka-compatible endpoint. This service used `github.com/twmb/franz-go` first, then switched to `kafka-go` specifically for its MIT license (franz-go is BSD-3-Clause) — both are pure Go (no cgo), keeping this service on Choreo's buildpack deploy with no Dockerfile either way; the swap is otherwise a wash technically (see the two known trade-offs below). `dispatch` and any other caller never import `kafka-go` directly — this package exposes its own `Record{Topic, Partition, Offset, Key, Value}` and `Handle func(context.Context, Record) error` instead, so `github.com/segmentio/kafka-go` is fully contained here. Auth is SASL/PLAIN with the literal username `"$ConnectionString"` and the Event Hub namespace's Shared Access Policy connection string as the password — this is Event Hub's own convention, not a real username. `Producer.Publish` keys every record by `EntityID` (`kafka.Hash` balancer) so all events about one case/incident land on the same partition and are processed in order. `Consumer.Run` uses `FetchMessage`/`CommitMessages` (not the auto-committing `ReadMessage`) and only commits a record's offset after `Handle` succeeds (or exhausts `handleAttempts` retries) — never before — so a crash mid-processing redelivers on restart instead of silently skipping. `Compression` is left unset (no codec) on the `Writer` — Event Hub's Kafka-compat layer rejected both idempotent producing and compressed batches with `UNSUPPORTED_FOR_MESSAGE_FORMAT` under the previous client (confirmed against the real namespace); `kafka-go`'s `Writer` has no idempotent-write feature to disable in the first place, and leaving `Compression` unset avoids the same rejection. `StartOffset: kafka.FirstOffset` is set explicitly for the same reason `kgo.ConsumeResetOffset(...AtStart())` was needed before — a partition with no committed offset should be read from the beginning, not the tail — though this happens to already be `kafka-go`'s own default. `logger.go` bridges kafka-go's `Logger` (routine, non-error chatter — protocol join/sync/commit messages, "N messages written" on every produce) to `slog.Debug`, and `ErrorLogger` (where kafka-go actually reports problems) to `slog.Error` — matching kafka-go's own severity split. Confirmed against the real namespace: routing `Logger` to `slog.Warn` instead (as this package originally did, to compensate for the previous Kafka client only having one log level) produced thousands of WARN lines a day for entirely normal operation. Don't reach for per-message-string filtering here again — bridging at the right level per kafka-go's own Logger/ErrorLogger split makes that unnecessary.
  - **Known trade-offs from the franz-go → kafka-go swap** (confirmed live against the real Event Hub namespace, not theoretical): (1) `kafka-go`'s consumer-group rebalancing only offers `Range`/`RoundRobin` balancers, no cooperative/incremental strategy like franz-go's `CooperativeStickyBalancer` — only matters once this service runs more than one instance, where a rebalance will briefly pause every partition instead of just the ones moving. (2) A graceful `Consumer.Close()` (and therefore full process shutdown, since it's deferred after the HTTP server's own 15s `Shutdown`) can take up to ~30s, matching `kafka.ReaderConfig.SessionTimeout`'s default — noticeably slower than before. If this service is ever deployed somewhere with a shorter termination grace period than server-shutdown-timeout + ~30s, that's worth revisiting (e.g. lowering `SessionTimeout` explicitly).
- **`internal/dispatch`** (`dispatch.go`) — `Dispatcher.Handle` implements `eventbus.Handle`: unmarshal the record as an `events.Envelope`, switch on `Type`, unmarshal `Payload` into the matching struct, then react. Four types (`case.*`) call the matching `notifications.Render*` function and send the result via `EmailClient.SendEmail` to that payload's own `Recipients` field — `Dispatcher` itself holds no recipient state; `send`'s `recipients []string` parameter is a genuine per-call argument, not a stored default. `incident.created` is different — no template, no email — it calls `GoogleChatClient.SendIncidentAlert` and `TwilioClient.MakeCall` directly from the payload's own fields, attempts both even if one fails, and combines their errors with `errors.Join`. A non-nil return from `Handle` is what triggers `eventbus.Consumer`'s retry — which is exactly why `handleIncidentCreated` needs its own per-channel idempotency tracking (`Dispatcher.done`, keyed by `topic/partition/offset/channel`): without it, a persistently-failing call would cause the already-succeeded chat alert to be resent on every retry too. This was a real bug caught by testing against Twilio being unconfigured — see that function's doc comment before changing this. `done` entries are released either when both channels have succeeded, or when `record.IsFinalAttempt` is true (set by `eventbus.Consumer.handleAndCommit` on the last of `handleAttempts` calls) — the latter matters because a channel that never succeeds would otherwise never hit the "both succeeded" branch, leaking its tracking entry forever; `IsFinalAttempt` says no further retry is coming for this record either way, so it's safe to stop tracking regardless of outcome.
- **`internal/handler/events.go`** — `EventsHandler.PostEvent`: strict validation (`DisallowUnknownFields`, reject trailing JSON via a second `Decode` requiring `io.EOF`, reject unknown top-level fields), plus per-`Type` required-field checks in `validateEventPayload`. Publishes the **original validated request body** unchanged (not a re-marshaled struct) — the dispatcher decodes it the same way, so there's exactly one JSON shape in play end to end.
- **`cmd/server/main.go`** — constructs `eventbus.Config` from `mustEnv` (not `os.Getenv`): unlike the notification channels, a broken event bus config should fail startup loudly since consuming events is this service's core job. Starts `consumer.Run(ctx, dispatcher.Handle)` in a goroutine alongside the HTTP server, sharing the same shutdown context so both stop together on SIGTERM/SIGINT.

### Adding a new event type

1. **Payload struct** (`internal/events/events.go`) — add a `<Name>Payload` struct with every field its eventual `Render*` call needs (plus `Recipients []string` if it emails anyone — see `CaseCreatedPayload`), and a new `Type` constant added to `KnownTypes`
2. **Validation** (`internal/handler/events.go`, `validateEventPayload`) — add a case decoding and checking the new payload's required fields
3. **Dispatch** (`internal/dispatch/dispatch.go`) — add a case in `Handle`'s switch and a `handle<Name>` method following the existing ones' shape
4. **Template**, if new — see "Adding a new channel"'s sibling process in `internal/notifications`
5. **Tests** — add handler validation tests (`internal/handler/events_test.go`) and dispatch tests (`internal/dispatch/dispatch_test.go`) following the existing per-type cases

## Running locally

```bash
# from integrations/csm-notification-service
go run ./cmd/server/main.go
```

The server auto-loads `.env` from the working directory at startup (silently ignored if absent).

## Commands

```bash
go vet ./...              # vet
go test -race ./...       # vet + race-detector tests
go build -o server ./cmd/server   # compile
govulncheck ./...         # checks dependencies against Go's official vulnerability database
```

`govulncheck` does call-graph analysis, not just "is a vulnerable package present" — it only flags a vulnerability if your code's own call graph actually reaches the vulnerable function, so a clean result means more than a plain dependency-list scan would. If it errors with `package requires newer Go version go1.26 (application built with go1.25)`, the installed `govulncheck` binary itself was built with an older Go than this module's `go 1.26.0` directive — reinstall it with a toolchain that matches or exceeds that, e.g. from a directory using that toolchain, or `GOTOOLCHAIN=go1.26.5 go install golang.org/x/vuln/cmd/govulncheck@latest` (adjust the patch version to whatever's cached under `$(go env GOPATH)/pkg/mod/golang.org/toolchain@v0.0.1-go1.26.*`), then invoke it the same way if it still misdetects its own Go version.

## Adding a new channel

1. **Client** (`internal/notifications/<channel>.go`) — add `<Name>Config`/`<Name>Client`/`Send<Thing>` following `email.go`'s or `googlechat.go`'s shape, whichever auth scheme is closer
2. **`cmd/server/main.go`** — construct the new client from env vars (use `os.Getenv`, not `mustEnv`, unless the channel truly must be configured for the service to start), and pass it into `dispatch.NewDispatcher`
3. **`dispatch.Dispatcher`** — add a field for the new client, and call it from whichever `handle<Type>` method(s) should trigger it (a new field on an existing event's payload if it needs new caller-supplied data, or a new event type entirely — see "Adding a new event type")
4. **`openapi.yaml`** — if the new channel needs new payload fields, add them to the relevant `*Payload` schema
5. **Tests** — add dispatch tests for the new channel's send path, following the existing per-type cases in `dispatch_test.go`

## Security

- **Never commit secrets** — client IDs/secrets, webhook URLs, service URLs with credentials, and the Event Hub connection string must not appear in source code or config files; use environment variables
- **No sensitive data in logs** — log only IDs and error summaries; this includes not logging the Event Hub connection string or full record values that might carry PII — every `case.*` payload's `recipients` array is real email addresses now (not a fixed test list), so this applies more directly than before
- **No app-level inbound auth** — this is intentional (see above), not an oversight; don't "fix" it by bolting on JWT validation without confirming the Choreo gateway model has changed
- **Input validation** — validate and reject unexpected input at the boundary (body size, JSON structure, required fields) before any future dispatch or queue publish
- **TwiML injection** — `MakeCall`'s spoken message is caller-supplied text, not trusted markup. `sayTwiML` (`twilio.go`) builds the `<Say>` document by `encoding/xml`-marshaling a typed struct (`twimlResponse`/`twimlSay`), never raw string concatenation — a message containing TwiML-shaped text (e.g. `</Say><Redirect>...`) must render as literal spoken text, not inject a different verb. `Voice`/`Language` go through the same struct as `xml:"...,attr"` fields, so they get correct attribute escaping too, even though today they're only ever operator-supplied config, not request input. Keep using `encoding/xml` struct marshaling (not string concatenation) for any future TwiML-building code in this package
- **Security fixes in PRs** — describe security-related changes in neutral functional terms only, not called out as security fixes in the title/description
- **Run `govulncheck ./...` on dependency changes** — alongside `gosec` (which only analyzes this repo's own code), run this whenever `go.mod`/`go.sum` changes (a new dependency, or a version bump) to catch known vulnerabilities in the dependency tree itself. It must report 0 vulnerabilities reachable from our code before opening a PR; a vulnerability present in a dependency but not reachable through anything we call is worth noting in the PR but isn't a blocker — see `internal/eventbus`'s `klauspost/compress` bump for a real precedent (GO-2026-5841, upgraded proactively even though unreachable, since the fix was free)
